5 Endpoint Strategy Confirmation

✅ AGREED: A NEW endpoint GET /api/compare-universities?ids=123,456,789 is the cleanest and safest approach.

Reasons to AGREE

  • No Breaking Changes: Existing /api/program-details remains untouched
  • Clean Response Shape: University-centric vs program-centric
  • Single Request: Frontend makes 1 call instead of N+1
  • Aggregation Server-Side: Tuition min/max, program count, levels — computed in backend
  • Easy to Test: Isolated endpoint, easy to validate independently

Risks of Extending Existing API (Why NOT to do it)

  • Would need to add ?ids= parameter to /api/program-details
  • Response shape would need conditional logic (program list vs university summary)
  • Pagination becomes complex with aggregation
  • Risk of breaking existing consumers of the API

6 Aggregation Feasibility

Aggregation Feasibility SQL/Python Approach Performance Notes
Tuition min/max ✅ Feasible MIN(CAST(attributes->>'tuition' AS FLOAT)), MAX(...) grouped by school_id Single query, JSONB indexed. Fast for 4 universities.
Program count ✅ Feasible COUNT(*) grouped by school_id Very fast.
DISTINCT levels ✅ Feasible ARRAY_AGG(DISTINCT attributes->>'level') grouped by school_id Efficient with proper indexing.
Scholarship count ✅ Feasible COUNT(*) from scholarships grouped by schoolGroupId Separate query or LEFT JOIN. Fast.
Top 3-5 programs ⚠️ Needs Definition Order by what? Tuition? Alphabetical? Would need LIMIT 5 per university. Feasible but needs clarification on sort order.

Performance Concerns

⚠️ Potential Risks:
  • JSONB Extraction: Casting attributes->>'tuition' to Float across many rows. Mitigated if filtered to specific school_ids.
  • 4-University Limit: With max 4 universities, query size is bounded. No N+1 issue.
  • No Indexes on JSONB: If attributes["tuition"] is not indexed, aggregation may be slower. Recommend testing on real data volume.
Recommendation: For V1 with 4 universities, performance is not a blocker. Consider adding JSONB index on tuition if scaling needed later.
