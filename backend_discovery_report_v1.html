3 API Capability Review

3.1 Existing Endpoint Analysis

Endpoint Can Support Multi-University Comparison? Reasoning
GET /universities/{school_id} ❌ NO Only fetches ONE university per request. Would require 4 separate calls.
GET /api/programs/{program_id} ❌ NO Program-centric, too granular. Does not aggregate.
GET /api/program-details ❌ NO • university_name filter only accepts ONE value
• Returns program list, not university summaries
• No aggregation logic
• Would cause N+1 queries
GET /scholarships/{school_id} ⚠️ PARTIAL Could be used per-university, but adds N calls

3.2 Would Reusing Existing APIs Cause Problems?

Problem Answer Details
N+1 Query Problem? YES Comparing 4 universities would require: 4× university + 4× programs + 4× scholarships = 12 API calls minimum
Client-Side Aggregation? YES Frontend would need to compute tuition ranges, counts, levels from raw program data
Breaking Changes? YES (if extended) Adding ?ids= to /api/program-details would change response shape
❌ CONCLUSION: Existing endpoints CANNOT efficiently support multi-university comparison. A new endpoint is required.

Method GET
Parameter ids — comma-separated university IDs
Max IDs 4

4.2 Why Extending Existing Endpoints is RISKY

Risk Impact
Breaking Changes Existing consumers of /api/program-details expect program arrays, not university summaries
Mixed Responsibilities Endpoint currently lists programs; adding university aggregation violates single-responsibility principle
Pagination Conflicts Current endpoint is paginated (page, page_size); aggregation per university doesn't fit this model
Filter Conflicts Existing filters (min_fees, program_name) don't make sense for comparison view
Testing Complexity Would need to regression-test all existing use cases

4.3 Why a New Endpoint is SAFER

Benefit Details
Zero Breaking Changes Existing APIs remain completely untouched
Clean Response Shape Purpose-built for comparison — no conditional logic needed
Single Request Frontend makes 1 call instead of 12+
Server-Side Aggregation Backend computes everything — lightweight frontend
Easy Testing Isolated endpoint — easy to unit test
Clear Ownership Single endpoint for comparison feature — easy to maintain and evolve
✅ VALIDATED: Creating GET /api/compare-universities is the correct architectural decision. Do NOT extend existing endpoints.

5 Aggregation Feasibility

5.1 Aggregation Strategies

Aggregation SQL Strategy (Pseudocode) Performance
Tuition Min/Max 
SELECT school_id,
  MIN(CAST(attributes->>'tuition' AS FLOAT)) AS tuition_min,
  MAX(CAST(attributes->>'tuition' AS FLOAT)) AS tuition_max
FROM program_details
WHERE school_id IN (?, ?, ?, ?)
GROUP BY school_id
 Fast — Filtered by 4 IDs, single table scan
Program Count 
SELECT school_id, COUNT(*) AS program_count
FROM program_details
WHERE school_id IN (?, ?, ?, ?)
GROUP BY school_id
 Very Fast
Distinct Levels 
SELECT school_id,
  ARRAY_AGG(DISTINCT attributes->>'level') AS levels
FROM program_details
WHERE school_id IN (?, ?, ?, ?)
GROUP BY school_id
 Fast
Scholarship Count 
SELECT schoolGroupId, COUNT(*) AS scholarship_count
FROM scholarships
WHERE schoolGroupId IN (?, ?, ?, ?)
GROUP BY schoolGroupId
 Very Fast
Top 5 Programs 
SELECT * FROM (
  SELECT school_id, attributes->>'name' AS program_name,
    ROW_NUMBER() OVER (
      PARTITION BY school_id 
      ORDER BY attributes->>'name'
    ) AS rn
  FROM program_details
  WHERE school_id IN (?, ?, ?, ?)
) sub WHERE rn <= 5
 Moderate — Window function, bounded by 4 IDs

5.2 Performance Considerations

Concern Risk Level Mitigation
JSONB extraction overhead Low Query is filtered to max 4 school_ids — bounded data size
CAST operations Low Already proven in existing /api/program-details implementation
Multiple table queries Low Can parallelize or combine with UNION/subqueries
Large result sets N/A Max 4 universities returned — result size is tiny

5.3 Known Risks

  • NULL Tuition: Some programs may have NULL or invalid tuition. Use COALESCE or filter nulls.
  • Empty Programs: A university may have 0 programs in program_details. Return zeros gracefully.
  • String Parsing: Tuition stored as string — ensure valid numeric conversion.
✅ AGGREGATION IS FEASIBLE: All required aggregations can be performed efficiently. Max 4 universities ensures bounded query complexity.
