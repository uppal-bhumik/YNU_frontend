3 API Capability Review

3.1 Existing Endpoints Analysis

Endpoint Method Purpose Reusable for Compare?
/universities/{school_id} GET Fetch single university by ID ⚠️ Limited — One at a time
/api/programs/{program_id} GET Fetch single program details ❌ No — Too granular
/api/program-details GET List programs with filters ⚠️ Partial — Program-centric, not university-centric
/scholarships/{school_id} GET Fetch scholarships for one university ✅ Yes — Can be used per university

3.2 /api/program-details — Deep Analysis

Feature Current Behavior Comparison Need
Filters Supported university_name, program_name, country, min_fees, max_fees Need ?ids=123,456,789 for multi-select
University Selection Single university_name (partial match) Need multiple IDs simultaneously
Response Shape Array of individual programs Need university-centric aggregates
Aggregation None — returns raw program data Need tuition min/max, counts, levels

3.3 N+1 Query Problem

⚠️ Using existing APIs would cause N+1 issues:
  • To compare 4 universities:
  • 4 calls to /universities/{id}
  • 4 calls to /api/program-details?university_name=...
  • 4 calls to /scholarships/{id}
  • Total: 12 API calls minimum
  • Frontend must aggregate data client-side
  • Slow, inefficient, and error-prone
⚠️ CONFIRMED: Current APIs cannot efficiently support multi-university comparison. A new endpoint is required.

4 Endpoint Strategy Validation

4.1 Proposed New Endpoint

GET /api/compare-universities?ids=123,456,789
Parameter Type Required Validation
ids String (comma-separated) Yes Max 4 IDs, must be valid university IDs

Risk Details

Mixed Responsibilities Endpoint currently returns programs; adding university aggregates mixes concerns
Pagination Complexity Current endpoint is paginated; aggregation per university doesn't fit this pattern
Filter Conflicts Existing filters (min_fees, program_name) don't make sense for comparison view

4.3 Why a NEW Endpoint is SAFER

Benefit Details

Single Request Frontend makes 1 call instead of 12+
Server-Side Aggregation Backend computes tuition ranges, counts — no client-side processing
Easy Testing Isolated endpoint, easy to validate independently
Clear Ownership Single endpoint for comparison feature — easy to maintain

5 Aggregation Feasibility

5.1 Aggregation Requirements

Aggregation SQL Strategy Performance
Tuition Min/Max 
SELECT 
  school_id,
  MIN(CAST(attributes->>'tuition' AS FLOAT)) as tuition_min,
  MAX(CAST(attributes->>'tuition' AS FLOAT)) as tuition_max
FROM program_details
WHERE school_id IN (123, 456, 789)
GROUP BY school_id
 ✅ Fast — Single query, filtered by IDs
Program Count 
SELECT 
  school_id,
  COUNT(*) as program_count
FROM program_details
WHERE school_id IN (123, 456, 789)
GROUP BY school_id
 ✅ Very Fast
Distinct Levels 
SELECT 
  school_id,
  ARRAY_AGG(DISTINCT attributes->>'level') as levels
FROM program_details
WHERE school_id IN (123, 456, 789)
GROUP BY school_id
 ✅ Fast
Scholarship Count 
SELECT 
  schoolGroupId,
  COUNT(*) as scholarship_count
FROM scholarships
WHERE schoolGroupId IN (123, 456, 789)
GROUP BY schoolGroupId
 ✅ Very Fast
Top 5 Programs 
-- Per university, using window function
SELECT * FROM (
  SELECT 
    school_id,
    attributes->>'name' as program_name,
    ROW_NUMBER() OVER (PARTITION BY school_id ORDER BY attributes->>'name') as rn
  FROM program_details
  WHERE school_id IN (123, 456, 789)
) sub
WHERE rn <= 5
 ⚠️ Slightly Complex — Window function, but bounded
